# P1/P2: корректность данных и общая архитектура

Изменения от 16 октября 2026.

## Парсинг и проверка

- Неделя определяется явным заголовком `I/II неделя`, либо проверенным форматом портала: два полных последовательных блока Пн–Сб. Цвет шрифта не читается. Частичные, противоречивые и неизвестные структуры не распределяются по неделям предположительно.
- Заголовки пар и интервалы времени разбираются совместно. Пустые хвостовые столбцы экспорта не становятся придуманными парами. Если в столбце есть занятия, но нет номера/времени, таблица получает ошибку.
- Дни заочников берутся из первой ячейки, включая воскресенье. Явная дата хранится отдельно; дата без года не получает выдуманный год или вычисленный день недели. Если в ячейке есть `Вск,12 апреля`, индекс воскресенья сохраняется из этого текста.
- Низкоуровневый разбор неизвестной структуры выбрасывает `ScheduleStructureError`. Общий слой возвращает `is_incomplete`, `parse_errors` и пустые недели вместо ошибочного расписания. Сайт показывает «Данные неполные», а не свободный день. Фоновая синхронизация отклоняет такую новую страницу, сохраняя прежний файл.
- Несовпадение имени группы и каталога также публикуется как явное неполное расписание без чужих занятий. Повреждённые исходники не исправляются догадками.
- `teachers_meta.json` кэшируется по пути, `mtime_ns` и размеру. Внешнее изменение файла автоматически перечитывается; ручное сохранение сбрасывает кэш. Возвращаются копии, чтобы вызывающий код не изменил сохранённые данные.
- `logging` содержит ошибки источника и контекст. `/api/status` и статические `api/status.json`, `api/catalog-status.json` содержат счётчики и до 50 последних сообщений. Статические счётчики относятся к одной сборке; динамические — к текущему процессу, а не ко всей истории сервера. Статистика показана в «Данные расписания».

## Общий слой и индекс аудиторий

`esstu_schedule/data/models.py` содержит dataclass-модели и проверку границы расписаний, пар, занятий и результатов загрузки. Динамический сервер, каталог и сборщик используют `data/repository.py`. Дополнительные поля происхождения данных сохраняются в JSON.

`/api/rooms` только читает готовый JSON, кэшируя чтение по `mtime_ns`/размеру. Запрос не обращается к порталу, не сканирует кафедры или группы и не строит индекс. При отсутствии или повреждении JSON возвращается 503 с понятной причиной в журнале. Нет автоматического дорогого обхода в HTTP-потоке.

Сборщик атомарно обновляет `dist/api/rooms.json` для Pages и `cache_store/rooms.json` для динамического сервера. Второй файл переживает пересоздание `dist/`. Переменные `ESSTU_SNAPSHOT_DIR` и `ESSTU_ROOMS_INDEX` позволяют выбрать каталог/файл. При ошибке до публикации нового индекса предыдущий runtime-файл сохраняется.

Фоновая команда для cron/планировщика:

```sh
python -m scripts.sync_esstu
python -m scripts.build_static_site
```

На Pages эта последовательность выполняется существующим расписанием Actions; динамическому хостингу нужна собственная такая задача. Render-сборка уже создаёт начальный индекс. Сам HTTP-сервер задачу синхронизации не запускает.

## Кэш запросов

У запросов к одному ключу есть отдельная блокировка с удалением неиспользуемых блокировок. До 15 минут результат свежий. От 15 минут до часа возвращается помеченная сохранённая версия, а ровно одна задача на ключ обновляет данные в фоне. Старше часа или при принудительном обновлении запрос ждёт результата. Одновременно работают до четырёх фоновых обновлений. Исключение не обновляет время успешного кэша и пишется в журнал. Это кэш внутри одного процесса, не распределённая блокировка нескольких серверов.

## Структура и воспроизводимость

- `esstu_schedule/` — реализация; `data/` — модели, общий доступ к данным, диагностика и JSON-хранилище.
- `scripts/` — сборка и синхронизация; старые корневые Python-файлы оставлены как совместимые точки входа.
- `tests/fixtures/` — шесть зафиксированных HTML из `demo_data`, SHA-256 и ожидаемые JSON. Для кафедры проверяется первый преподаватель полного исходного HTML; профили берутся без изменяемых локальных метаданных. CI никогда не перезаписывает ожидаемые результаты.
- `tests/` — Python-тесты, включая табличные даты границ сентября, воскресенья и смены года, часовой пояс Улан-Удэ, внешний `mtime`, неполные таблицы, фоновый кэш и отсутствие сканирования в rooms HTTP.
- `e2e/unit/` — быстрые проверки JS; они сохраняют отдельную роль и не выдаются за браузерные тесты.
- `e2e/*.spec.cjs` — настоящие Playwright-тесты Chromium на desktop и мобильном экране: расписание, статус качества, выбор преподавателя, неполные данные, адреса PWA и офлайн-запуск под префиксом Pages.
- Разбор HTML использует `lxml`. `requirements.in` фиксирует прямые версии, `requirements.txt` создан `uv pip compile requirements.in --generate-hashes -o requirements.txt`; установщик использует `--require-hashes`. Node-зависимости зафиксированы в `package-lock.json` и устанавливаются через `npm ci`.

Проверки:

```sh
pip install --require-hashes -r requirements.txt
python -m unittest discover -s tests -t .
npm ci --ignore-scripts
npm run build:css
python -m scripts.build_static_site
npm run test:unit
npx playwright install chromium
npm run test:e2e
```

Браузерные тесты проверяют запуск через сохранённую оболочку, но не заменяют установку на реальном Android/iOS. Нагрузочные измерения и распределённый кэш в эту проверку не входят.
